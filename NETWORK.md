# Основа совместной работы

Статус версии 1.4: локальное приложение. В коде нет сетевого транспорта, удалённой базы, сессий, действующих приглашений или платежей. Все перечисленные ниже серверные маршруты — проект контракта, их ещё нет.

## Что реализовано

`collaboration.mjs` выделяет общий набор данных: inventory, events, shelves, activity. У записей уже есть стабильные id. Локальная метаинформация содержит workspaceId, общую revision, records с версиями отдельных записей и deleted с отметками удаления. Одна успешная операция может обновлять несколько записей с одной ревизией (например, продажу в маркете и склад). Черновик расчёта и настройки интерфейса остаются локальными.

`recordWorkspaceChanges` вызывается внутри commit, перед проверкой и сохранением. Ошибка сохранения не заменяет состояние в памяти. Перезагрузка сохраняет идентификатор пространства. Импорт резервной копии создаёт новое пространство, чтобы будущая синхронизация не приняла восстановление старой копии за свежие правки удалённых данных.

`workspaceSnapshot` возвращает отдельную копию общего состояния для будущей первоначальной загрузки. Фотографии пока хранятся в IndexedDB и в JSON-копиях, в сетевом снимке остаются только их id. Ни initData, ни отображаемый профиль, ни локальные настройки в снимок не входят.

Это задел для первой загрузки и определения изменений, **не журнал операций и не механизм слияния**. Клиентская revision не заменяет версию сервера. До включения совместного режима понадобится слой команд и транзакций. Автоматически смешивать копии с разных устройств по времени сохранения нельзя.

## Следующий этап: сервер

1. Сессия: `POST /session/telegram` получает initData, проверяет подпись Telegram и срок auth_date. Сервер берёт userId только из проверенных данных; клиентский workspaceId не даёт прав доступа.
2. Первоначальный импорт: отдельная подтверждаемая загрузка локального пространства и фото; сервер создаёт владельца и присваивает канонический workspaceId. При входе со второго устройства выбирается существующее пространство, вместо молчаливого объединения запасов.
3. Команды: `POST /workspaces/:id/commands` с operationId (UUID), baseRevision, type и payload. Примеры: stock.add, event.sale, event.close, event.undoSale, shelf.transfer. Сервер повторно проверяет данные и права, выполняет команду одной транзакцией. Повтор operationId возвращает исходный результат, а не вторую продажу.
4. Конфликты: при несовпадении версии — 409 и актуальная версия. Перед повтором пользователь видит изменённые остатки. Продажи и закрытие маркета пересчитываются на сервере атомарно, чтобы два помощника не продали один последний товар.
5. Получение изменений: `GET /workspaces/:id/changes?cursor=...` с устойчивым серверным курсором, обновлениями и удалениями. Затем WebSocket/SSE для быстрого обновления; после обрыва — догрузка по курсору.
6. Офлайн: очередь команд в IndexedDB с operationId и состоянием подтверждения, отдельная индикация неподтверждённых продаж. Локальные изменения нельзя выдавать за подтверждённые другим устройством. До реализации этого протокола совместные продажи следует разрешать только при связи с сервером.
7. Фото: отдельная загрузка с ограничением размера, ссылкой по id и проверкой доступа; серверное удаление только после проверки ссылок из исторических записей.

## Помощники и ссылки

Для первого сетевого выпуска достаточно помощников конкретного маркета. Владелец видит и меняет весь свой склад, цены и отчёты. Помощник видит выданный ему маркет и вносит продажи; не удаляет склад, не меняет цены и не завершает маркет. Это предлагаемые роли, ещё не реализованные.

Владелец запрашивает приглашение на сервере. Сервер создаёт случайный одноразовый токен с назначением, сроком и возможностью отзыва; хранит его хеш. Ссылка: `https://t.me/so1ankamerchbot?startapp=invite_<token>`. Запуск ссылки сам по себе не даёт доступа: после авторизации сервер проверяет токен и запрашивает явное присоединение. Токен не содержит открытых данных склада или номера телефона. Список друзей можно добавить позже поверх серверных пользователей и явного принятия приглашений.

## Оплата по QR

Идея для следующего этапа: к маркету прикрепляется платёжная ссылка или изображение QR, кнопка «Принять оплату» показывает его покупателю. Показ QR не означает успешную оплату. Подтверждение платежа вручную и автоматическое подтверждение через банковский API/webhook — разные режимы. Продажа и оплата должны иметь отдельные id, статусы и защиту от повторного учёта. Текущая версия не обрабатывает платежи.

## Профиль Telegram

`telegramProfile` использует имя и необязательный photo_url только для отображения. Фото загружается по HTTPS, при отсутствии или ошибке показывается буква имени. Вне Telegram — нейтральный профиль. initDataUnsafe не является подтверждением личности и не даёт права на чужие записи.

Официальный источник: [Telegram Mini Apps — данные пользователя и проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
